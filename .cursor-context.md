# Printer NVR - Cursor Context

## Project name
Printer NVR

## Project purpose
Printer NVR is a minimal web-based recording system for 3D printers.

Printers expose camera streams through go2rtc.

The app provides a lightweight web UI that lets the user:
- view multiple printer cameras
- start recording
- stop recording
- optionally set a duration so recording stops automatically
- manage cameras through a config-backed web UI
- manage printers and nested camera views through a printer-first config UI
- monitor grouped printers on a live dashboard page
- watch all printer cameras on a compact camera wall page
- browse, download, and manually delete local clips
- mark clips as favorites or rejected during review
- safely rename clips from the browser
- preview clips inline and bulk-download selected clips as direct individual files
- optionally save clip downloads into a user-selected browser folder on supported browsers
- review the latest clip for a selected printer view directly from the live printer card

Recording is performed by ffmpeg on a central host, not on the printers.

Printers only provide camera streams.

Recordings are written locally on the recorder host.

NAS syncing or archival is outside the MVP unless explicitly added later.

## Core architecture decisions
- Printers are stream sources only
- go2rtc is expected but Printer NVR should remain a generic stream consumer
- Printer NVR runs on a separate recorder host
- ffmpeg runs on the recorder host
- RTSP recording inputs should use TCP transport by default
- recording should target the primary video stream by default rather than copying all streams into MP4
- live printer cards should group cameras by printer and use one default live view per printer in this phase
- recordings are stored locally on the recorder host
- Docker-first deployment
- GitHub repository is the source of truth
- Keep architecture simple and maintainable

## Camera configuration model

Printer NVR actively supports go2rtc helper and manual URL camera modes.

Legacy compatibility note:
- `mode=gopro` still exists in code for backward compatibility, but it is no longer part of the active project direction

Printer-first config is the preferred shape:
- top-level `printers`
- each printer has `id`, `name`, `enabled`, optional `moonraker_url`, `display_order`, `default_camera_id`
- each printer contains one or more nested camera views

Legacy camera-first config remains supported and may include lightweight printer grouping fields:
- `printer_id`
- `printer_name`
- `default_live_view`
- `moonraker_url`
- `display_order`

### go2rtc helper mode

The user may provide:
go2rtc_base_url  
stream_name (optional)

Example fields:

id: sv08_left  
name: SV08 Left  
go2rtc_base_url: http://sv08-left.local:1984  
stream_name: cam  
enabled: true  
output_subdir: sv08_left

The system may derive likely URLs:

preview -> http://host:1984/stream.html?src=cam  
record -> rtsp://host:8554/cam

This is a convenience helper only.

### manual URL mode

The user may provide explicit URLs:

preview_url  
record_url

Example fields:

id: sv08_left  
name: SV08 Left  
preview_url: http://sv08-left.local:1984/stream.html?src=cam  
record_url: rtsp://sv08-left.local:8554/cam  
enabled: true  
output_subdir: sv08_left

### Resolution rules

Manual URLs override generated URLs.

record_url must exist after resolution.

Preview resolution order:
1. manual preview_url
2. generated go2rtc preview URL
3. no preview configured

Do not fall back to RTSP record_url for browser preview.

- camera preview
- recording start/stop

- live multi-printer overview page

## Deployment expectations

Printer NVR runs in Docker.

Persistent data should be bind-mounted from the host:

config  
recordings  
logs  

Planned Phase 11 deployment work:
- installer script for first-time Docker setup
- update script for pull/build/restart
- optional go2rtc companion Compose support
- external go2rtc must remain supported
- setup/update helpers must not overwrite existing config or recordings without backup/confirmation

The container should remain simple and single-purpose.

Tracked example config files should remain in the repo, but live deployment config files in `config/*.json` should stay untracked so local edits do not conflict with pulls.

## Known requirements

The app must start even if zero cameras exist.

If no cameras exist the dashboard should show an empty-state message.

Disabled cameras must not break startup.

RTSP streams must not be assumed to work directly in browser preview.

Recording and probe failures should expose useful ffmpeg/ffprobe diagnostics in runtime state and UI.

Client-side chosen-folder downloads must remain optional, browser-controlled, and never send local filesystem path information to the backend.

The live printer page should keep printer details below the preview area, not overlaid on top of the video.

The `/live` page is the compact camera wall:
- dark monitoring layout
- no recording controls
- no latest clip panels
- no clip review controls
- status/details below the video, not overlaid
- visibility toggles persisted in browser storage
- cards per row and rows per screen persisted in browser storage
- actively printing printers sorted ahead of non-printing cards
- normal polling must not rebuild cards, move DOM nodes, replace iframes, or reassign iframe `src`
- printing-priority sorting should use CSS `order` only
- Phase 10.4: optional secondary camera cards on `/live` only for printers with multiple views
- secondary live cards must be viewing-only and must not affect `/printers` selected view or recording targets
- secondary live card preferences are browser-local under `printernvr-live-secondary-views`
- secondary live cards should stay mounted and use CSS ordering to preserve iframe stability

The `/printers` page is the detailed monitoring and recording control dashboard.

The `/cameras` page is the Printers & Cameras management UI:
- create/edit/delete printers
- add/edit/delete nested camera views
- choose a default camera per printer
- save top-level `printers` config
- keep camera ids globally unique because recording/clips are camera-id based
- deleting config entries does not delete recordings

The `/printers` page now supports per-printer camera/view selection when multiple views exist.

Selected printer views should persist browser-side only and fall back to the backend-computed `default_live_view` when a stored camera choice becomes invalid.

The `/printers` page also supports lightweight monitoring polish:
- enlarged preview modal for the currently selected view
- normalized printer-state badges
- per-card freshness text for metadata updates
- manual refresh controls that reuse the existing polling path

The `/printers` page supports card-level recording controls:
- Start
- Stop
- quick timed buttons: 10s, 15s, 20s, 30s, 60s
- custom duration recording from 1-600 seconds

Printer-card recording actions must target the currently selected camera/view for that printer and reuse the existing `/api/record` backend paths.

Printer cards also show latest clip shortcuts for the currently selected camera/view:
- Preview Latest
- Download Latest
- View All Clips

Latest clip lookup must remain filesystem-based and reuse the existing clip store and secure clip endpoints.

Clip review metadata must remain filesystem-based sidecar JSON under the recordings root.

The export/copy helper must not be implemented until favorite, reject, rename, and filter workflows are fully working.

Legacy GoPro code may remain temporarily for compatibility, but it should not be expanded in new phases unless explicitly requested.
