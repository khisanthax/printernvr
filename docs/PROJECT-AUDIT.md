# Printer NVR project audit

**Reviewed:** November 22, 2026, at `a68bbb9` on `main`. This report covers recording and FFmpeg, timelapses, clip review, retention, printer monitoring, configuration, browser behavior, dependencies, and Docker deployment.

## Prioritized findings

### P0 | Protect recordings and control access

1. **Manual Stop can report success for an unreadable MP4. Confirmed on Windows.** The recorder closes stdin at launch, calls `terminate()` on stop, and treats any exit after a stop request as success. In a fixture run, the UI state became idle with a completed filename, but FFprobe reported `moov atom not found` on the 6,029,360-byte output. Linux FFmpeg commonly handles SIGTERM differently, so the test does not establish the same failure rate on the Docker host. Use a graceful FFmpeg stop, bounded escalation, an unpublished temporary file, and media validation before publishing. Wait for finalization on shutdown. [`recorder.py:80`](../app/recorder.py#L80), [`recorder.py:132`](../app/recorder.py#L132), [`recorder.py:202`](../app/recorder.py#L202)
2. **Stopping recordings lose deletion protection before finalization. Confirmed with runtime state.** `mark_stopping()` sets `recording=False`, while active paths include only `recording=True`. A concurrent clip rename, delete, or retention job can act on the unfinished file. A separate race releases the per-camera lock between checking and starting, and the monitor removes the job before publishing its terminal state. Concurrent starts can use the same second-resolution filename with `-y`. Claim a camera and its unique output before spawning, hold that claim through finalization, and share the ownership check across configuration, file mutations, and retention. [`state.py:97`](../app/state.py#L97), [`state.py:197`](../app/state.py#L197), [`recorder.py:59`](../app/recorder.py#L59), [`recorder.py:202`](../app/recorder.py#L202)
3. **The default deployment publishes unauthenticated administrative and media routes. Verified in source.** Compose exposes the port on all interfaces by default. The same app serves configuration, camera probing, file deletion, and recording controls without an application-level access gate. Actual exposure depends on the host firewall or existing proxy. Bind to localhost behind an authenticated proxy or restrict the port to the intended management network. Add access checks for sensitive routes, validate input URL schemes, and redact credentials and sensitive query strings from FFmpeg commands, diagnostics, and logs. The image also copies the entire `config/` directory. Copy only tracked examples and exclude private config and recordings from the Docker build context. [`docker-compose.yml:7`](../docker-compose.yml#L7), [`main.py:140`](../app/main.py#L140), [`api/cameras.py:125`](../app/api/cameras.py#L125), [`recorder.py:76`](../app/recorder.py#L76), [`Dockerfile:18`](../Dockerfile#L18)
4. **The declared dependencies force an affected Starlette version. Verified against upstream metadata.** FastAPI `0.115.8` requires Starlette `>=0.40.0,<0.46.0`. That entire range is affected by the `FileResponse` denial-of-service advisory fixed in `0.49.1`, and Printer NVR uses `FileResponse` to serve clips and timelapses. Upgrade and lock a compatible, currently patched dependency set, rebuild the image, and audit the installed dependency tree. The repo also pins Jinja `3.1.5`. Update it as part of the same pass. Its `3.1.6` sandbox fix has lower direct relevance because the app uses repository-owned templates. [`requirements.txt`](../requirements.txt), [FastAPI 0.115.8 dependency metadata](https://raw.githubusercontent.com/fastapi/fastapi/0.115.8/pyproject.toml), [Starlette advisory](https://github.com/Kludex/starlette/security/advisories/GHSA-7f5h-v6xp-fcq8), [Jinja release notes](https://github.com/pallets/jinja/releases/tag/3.1.6)

### P1 | Correct timelapse and retention behavior

5. **Deleting an old timelapse can clear or replace the active session's status. Confirmed with a fixture.** Deleting an older output calls a disk restore that overwrites `_states[printer_id]` even when a newer session remains active in `_sessions`. The test returned `idle` while the worker was still registered. Config edit checks use `_states`, so this can also hide a busy camera. Keep active runtime state separate from the latest completed output and only update the completed-output pointer on delete. [`timelapse.py:221`](../app/timelapse.py#L221), [`timelapse.py:263`](../app/timelapse.py#L263), [`timelapse.py:552`](../app/timelapse.py#L552)
6. **Timelapse publication and shutdown can expose partial output. Confirmed for listing and Stop state.** FFmpeg writes the final `.mp4` directly, and listing and startup recovery accept a matching file without validating it. A rendering fixture appeared in the output list. Stop during render changed its state to `stopping` without interrupting the render. Shutdown joins each worker for only two seconds while a capture or render may be blocked much longer. Render to a private temporary output and publish atomically after validation. Keep Stop idempotent and distinguish capture stop, render cancellation, and completion. Persist a small session manifest for camera attribution, frame count, and recovery of interrupted renders. [`timelapse.py:144`](../app/timelapse.py#L144), [`timelapse.py:175`](../app/timelapse.py#L175), [`timelapse.py:284`](../app/timelapse.py#L284), [`timelapse.py:402`](../app/timelapse.py#L402), [`timelapse.py:511`](../app/timelapse.py#L511)
7. **Retention treats media and source frames as interchangeable files. Verified in source.** The sweep walks the entire tree and chooses individual files by age without review state or session boundaries. It can delete a favorite, leave orphaned frames, or remove a session's source frames independently of its output. It protects only a snapshot of active filenames. Newly written frames can miss that snapshot. Manual cleanup also deletes in `alert_only` mode, which a fixture confirmed. The README describes that mode as calculating candidates only and separately documents manual cleanup as available in that mode. Make that distinction explicit with a visible dry run and confirmation. Protect session directories and active writes, serialize cleanup, and choose candidates by media type and review state. [`retention.py:59`](../app/retention.py#L59), [`retention.py:148`](../app/retention.py#L148), [`retention.py:206`](../app/retention.py#L206), [`timelapse.py:233`](../app/timelapse.py#L233), [`README.md:344`](../README.md#L344)
8. **Disk thresholds do not prevent an active capture from filling the volume. Verified in source.** Automatic retention runs at startup and after jobs finish. Manual recording has no maximum length, timed requests have no server-side upper bound, and there is no write-time free-space guard. Add a configurable low-water threshold checked before and during capture, then stop and finalize gracefully when necessary. Add idle/read timeouts and a bounded shutdown path. Cap timed input at the API, and periodically check storage independently of job completion. [`main.py:80`](../app/main.py#L80), [`main.py:106`](../app/main.py#L106), [`models.py:305`](../app/models.py#L305), [`recorder.py:177`](../app/recorder.py#L177)
9. **Browser auto-start infers a new job from a status change. Verified in source.** Resume after pause or a temporary Moonraker outage can retrigger the same job if no session is busy. Reloading the page or reopening another tab can also re-arm it. An unattended printer can start with no browser open and be missed entirely. Move opt-in auto-start into the recorder service, configure an explicit camera and interval per printer, and deduplicate by print job identity. Where job identity is unavailable, retain the last observed active job through pauses and outages. A manual Stop should suppress further starts for that job. Add a status explaining when auto-start is armed, paused, or unavailable. [`printers.js:970`](../static/printers.js#L970), [`printers.js:1495`](../static/printers.js#L1495), [`timelapse.py:326`](../app/timelapse.py#L326)

### P1/P2 | Correct the clip and configuration model

10. **The clip index and file-serving rules disagree. Confirmed with a fixture.** The scanner listed a nested MP4 that its single-folder download resolver could not find, plus a non-video text file. The index excludes the timelapse namespace but the resolver does not share that exclusion. Adopt a shared completed-media policy for list, preview, download, rename, and delete. Reserve internal directories, block symlink escapes consistently, and reject ambiguous storage directory assignments. Store a consistent timestamp with timezone. Unix `ctime` describes metadata change rather than creation, which makes latest-clip order sensitive to file operations. [`clips.py:20`](../app/clips.py#L20), [`clips.py:111`](../app/clips.py#L111), [`clips.py:184`](../app/clips.py#L184), [`config.py:269`](../app/config.py#L269)
11. **Concurrent review edits can overwrite or lose metadata. Verified in source.** Sidecar updates read, modify, and replace one shared JSON file using one shared temporary name, without a store-level lock. File rename and delete happen before sidecar changes, so a metadata write failure leaves the file operation completed while the API reports an error. Lock review transactions, use unique staging paths, reconcile missing media and orphaned records, and avoid reporting that a file mutation failed if it already occurred. [`clips.py:123`](../app/clips.py#L123), [`clips.py:135`](../app/clips.py#L135), [`clips.py:155`](../app/clips.py#L155), [`clips.py:224`](../app/clips.py#L224)
12. **Whole-config edits can overwrite newer work, and empty printer records are lost at runtime. Verified in source.** Two browser tabs can save different drafts of the whole config without version checking. The legacy camera mutation paths can rebuild nested config from the flattened camera list, which cannot represent a printer with zero cameras. Config on disk and runtime state are updated in separate steps. Keep printer definitions as first-class runtime input, patch nested records directly, and check a config revision before committing a validated draft. Inventory output folders before adding uniqueness rules so existing media remains accessible. [`api/cameras.py:31`](../app/api/cameras.py#L31), [`api/cameras.py:153`](../app/api/cameras.py#L153), [`camera_store.py:55`](../app/camera_store.py#L55), [`config.py:343`](../app/config.py#L343), [`printers.py:16`](../app/printers.py#L16)

### P2 | Reduce unnecessary work and improve diagnostics

13. **Polling work grows with both camera count and files on disk. Verified in source.** Each cards request scans all recording paths once per view and again for each primary view. `/live` requests this clip data despite having no clip controls. Moonraker fetches run serially across printers. The root dashboard polls storage every four seconds, and storage status may scan files twice. Split live metadata from clip lookup, batch latest-clip discovery or scope it to camera directories, avoid traversing the timelapse tree for clips, and share a short-lived Moonraker snapshot between consumers. Keep iframe URLs stable and test record/timelapse actions through the same selected-view flow. [`printers.py:25`](../app/printers.py#L25), [`printers.py:99`](../app/printers.py#L99), [`retention.py:38`](../app/retention.py#L38), [`static/app.js:431`](../static/app.js#L431)
14. **Long recordings consume unnecessary memory in the recorder and optional browser saves. Verified in source.** FFmpeg stderr is collected until the subprocess exits, with no bound on accumulated progress logs. Browser folder saves buffer the entire response as a Blob. Drain FFmpeg output continuously with a bounded diagnostic tail and use structured progress for elapsed time and bytes. Stream supported browser responses to the destination and keep normal downloads as fallback. [`recorder.py:202`](../app/recorder.py#L202), [`static/clips.js:169`](../static/clips.js#L169), [`static/clips.js:681`](../static/clips.js#L681)
15. **Monitoring can confuse responsive HTTP with available printer data. Verified in source.** Moonraker's response shape is parsed outside the request error boundary. A malformed top-level response can break the cards endpoint, and missing `print_stats` can still be marked as fresh metadata. Validate the response and object values, distinguish offline from incomplete data, preserve last good readings, and keep the recorder host status separate from printer availability. [`moonraker_service.py:24`](../app/services/moonraker_service.py#L24), [`moonraker_service.py:44`](../app/services/moonraker_service.py#L44)
16. **Operational gaps make regressions harder to catch.** No tracked test suite or CI workflow was found. The health route does not verify FFmpeg availability, usable recordings storage, or free space, and the Compose file has no health check. Add a small test suite around manual/timed recordings, concurrent mutations, legacy/nested configuration, render recovery, and media access. Test the pinned Python 3.12 container as well as Windows behavior. Confirm no configuration depends on deprecated GoPro routes before removing them. [`api/health.py:11`](../app/api/health.py#L11), [`docker-compose.yml`](../docker-compose.yml), [`main.py:152`](../app/main.py#L152)

## Manual recording file sizes

Manual and timed FFmpeg recording use `-map 0:v:0 -an -c:v copy`. Timed recording adds `-t`. The camera's encoded video bitrate largely determines the file size. Measure the finished file's bytes and actual duration with FFprobe. Container overhead and variable bitrate make the formula an estimate.

`Estimated decimal MB = video Mbps × seconds ÷ 8`

| Video bitrate | 30 seconds | 60 seconds | 120 seconds | 1 hour |
| --- | ---: | ---: | ---: | ---: |
| 1 Mbps | 3.75 MB | 7.50 MB | 15 MB | 0.45 GB |
| 1.113 Mbps, historical go2rtc example | 4.17 MB | 8.35 MB | 16.70 MB | 0.50 GB |
| 2 Mbps | 7.50 MB | 15 MB | 30 MB | 0.90 GB |
| 4 Mbps | 15 MB | 30 MB | 60 MB | 1.80 GB |
| 8 Mbps | 30 MB | 60 MB | 120 MB | 3.60 GB |

The historical console log showed a **9.93-second H.264, 1920×1080, 15 fps** stream-copy sample at **1,113.1 kbps**, reported by FFmpeg as **1,350 kB**. That is approximately **1.38 decimal MB**. This is one observed stream sample. The local checkout contains only `recordings/.gitkeep`. The deployment host did not resolve by its known hostname, so this audit did not collect current manual recordings or infer a per-camera bitrate from configuration.

### Controlled compression comparison

One 10.13-second synthetic 1080p/15 fps H.264 clip was generated from a nominal 4 Mbps fixture and processed with the app's stream-copy command. Each candidate used the same frames, dimensions, and frame rate. Transcodes used the FFmpeg `fast` preset, a four-thread encoder setting, `yuv420p`, and MP4 fast-start. The encoding times are from this Windows host and exclude the input fixture generation. Production footage is needed to assess printer image quality.

| Encoding | Bytes | Change vs. stream copy | Local encode time |
| --- | ---: | ---: | ---: |
| H.264 stream copy | 5,415,467 | Baseline | n/a |
| H.264 CRF 20 | 5,907,171 | 9.1% larger | 2.76 s |
| H.264 CRF 23 | 4,625,614 | 14.6% smaller | 2.92 s |
| HEVC CRF 25 | 5,855,062 | 8.1% larger | 3.44 s |

These results justify a minimum-savings check. CRF controls quality and does not promise a bitrate or a smaller output. Codec and CRF values are not equivalent quality settings across encoders.

## Compression and space-saving plan

1. **Inventory real footage.** Collect at least three completed manual recordings per camera with representative print motion and lighting, including one longer clip to catch bitrate variation. Inventory the recorder host by camera and media class. Record duration, bytes, codec, resolution, fps, and review state. For each timelapse session, capture total JPG bytes, MP4 bytes, frame count, and interval. Report median and high-end MB/min and GB/day from actual usage. Show elapsed duration, live size estimate, and final size in Printer NVR. Keep the inventory read-only.
2. **Address timelapse storage first where source frames dominate.** Keep the current quality settings while measuring actual frames. At one capture every 10 seconds, an eight-hour print generates approximately 2,880 frames. At 250 KiB per frame, that is about 703 MiB before the final MP4. Add separate frame retention with a proposed seven-day recovery window after a verified render, and an option to keep frames for rerendering. Protect failed and active sessions and protect the final MP4 when expiring source frames. Test 10-, 15-, and 30-second capture intervals for longer prints where fewer frames are acceptable. Doubling the interval roughly halves source-frame storage and halves the resulting playback length at the same playback frame rate.
3. **Keep stream copy as the capture default.** It preserves the camera's original encoded stream and leaves CPU headroom during multiple recordings. Benchmark H.264 CRF 20, 22, and 23 on representative actual clips at source resolution and frame rate. Inspect first-layer details, nozzle motion, shadows, and texturing at native resolution and check browser preview and the intended social editor. Use HEVC only as an opt-in archive profile after playback and editing compatibility are confirmed. Where an upstream camera is producing an unnecessarily high bitrate, tune its encoder or choose a deliberate recording stream after comparing actual footage. At the same capture duration, reducing the source from 4 Mbps to 2 Mbps halves the expected size.
4. **Pilot an opt-in, post-recording Optimize action.** Start with one background encode at a time, adjustable CPU or thread limits, and no encode when storage is low or multiple captures are under load. Write into a hidden temporary file on the same filesystem. Keep the source until the candidate decodes, has the expected video and duration, and delivers at least **20% byte savings** as a starting threshold. Check metadata and path ownership immediately before an atomic publish. During the pilot, keep optimizations as separate copies for visual approval. Only enable optional in-place replacement once validation, ownership, and recovery tests pass. Preserve review flags and capture timestamps when replacing. If a job fails or is cancelled, keep the source and discard the temporary candidate. Leave favorites unmodified by default.
5. **Set retention policy after inventory.** Introduce a dry run that estimates reclaimed bytes and separates rejected clips, unreviewed clips, favorites, timelapse frames, and final timelapse MP4s. Start with automatic space alerts and configurable age limits for approved categories. Keep favorites and active sessions protected. Check headroom for the source and temporary output before a transcode. Track bytes saved, skipped encodes, CPU time, and finalization errors so policy changes can be judged on real results.

## Verification scope

- Reviewed the tracked application, templates, scripts, configuration, deployment, and documentation. Checked the local config load without logging connection details. Local config retention is disabled. Production retention configuration was unavailable.
- Recorded a paced synthetic source through manual Start/Stop on Windows. Verified the stopped output with FFprobe and benchmarked the same finalized stream-copy baseline against three encoding settings.
- Exercised isolated fixtures for active-file protection, old timelapse deletion, rendering output visibility, Stop during render, clip-index mismatch, and manual cleanup in alert-only mode. Remaining findings marked as source-based were not reproduced against production.
- Python source compilation, JavaScript syntax checks, and app import passed. All six page handlers rendered with fixture data and stubbed Moonraker status. A full local ASGI smoke test was blocked because even a minimal asyncio event loop stalled in this environment. The local Docker engine was unavailable. Physical cameras, current deployed settings, and end-to-end browser behavior remain unverified.
