# Printer NVR - Cursor Rules

These rules define how code should be written and how architectural decisions should be made when working on Printer NVR.

## Core Philosophy

Printer NVR is a **small, practical, self-hosted tool**, not a large platform.

The goals are:

- reliability
- simplicity
- maintainability
- low operational overhead

Avoid complexity unless it is clearly necessary.

Prefer simple solutions that are easy to understand and maintain.

---

# Architecture Rules

## Backend

The backend stack is:

- Python
- FastAPI
- ffmpeg subprocess calls

Do not introduce additional backend frameworks.

Avoid adding:

- Django
- Flask extensions unless necessary
- Celery
- Redis
- message queues
- event buses

The application should remain a **single process web server**.

Do not expand deprecated GoPro support unless the user explicitly requests legacy compatibility work. Current project direction is printer camera streams plus clip review workflow.
Do not present GoPro as an active camera type in normal UI flows; keep any remaining GoPro behavior as deprecated compatibility only.

---

## Frontend

Frontend must remain **simple**.

Allowed:

- HTML
- CSS
- minimal JavaScript
- Jinja templates

Do not introduce:

- React
- Vue
- Angular
- Svelte
- heavy frontend build systems

The UI should remain lightweight and server-rendered.

Live printer monitoring views should keep status/details below the preview area rather than overlaying them on video unless explicitly requested.

The `/live` camera wall must remain viewing-focused: no recording controls, duration controls, latest clip panels, or clip review controls. Keep `/printers` as the detailed control dashboard.
Optional secondary camera cards for `/live` must remain viewing-only and must not alter `/printers` selected-view behavior or any recording target behavior.
Secondary `/live` cards should stay iframe-stable during polling: do not rebuild/reload them during normal status refresh.
Multi-camera `/live` polish should keep primary and secondary card labels explicit, keep secondary controls understandable, and preserve CSS-order grouping without DOM reappend.

Camera wall density settings should remain browser-local and lightweight. Do not add backend preferences for cards per row, rows per screen, or camera-wall visibility unless explicitly requested.

Per-printer camera/view selection on `/printers` should remain browser-side only unless a later phase explicitly adds config-backed preferences.

Monitoring polish for `/printers` should prefer lightweight modal/dialog UI, polling, and graceful degraded states over heavier real-time infrastructure.

Printer-card recording controls must reuse existing camera-based recording APIs and always resolve actions through the currently selected camera/view for that printer card.

Printer-card timed duration controls should remain frontend affordances over the existing timed recording API. Do not add a separate duration subsystem.

Printer-card latest clip shortcuts must reuse the existing filesystem clip store and secure clip preview/download endpoints. Do not add a clip database or parallel clip index.

Timelapse controls belong on `/printers`, not `/live`. Timelapse capture uses a dedicated timelapse manager/API and must not overload the normal short-clip recording manager.

---

## Storage

Recordings are stored on the **local filesystem**.

Do not introduce:

- databases
- object storage
- cloud storage

All storage should be handled through the filesystem.

External archival (NAS, rsync, etc.) is handled outside the application.

Clip browsing and bulk download should remain direct-file based. Do not add ZIP packaging or server-side archive jobs unless explicitly requested.

Bulk clip delete should reuse the existing per-file delete path so path validation and active recording protections remain centralized.

Clip review metadata should use local sidecar JSON under the recordings root. Do not add a database, server-side clip index, or export/copy workflow before favorite, reject, rename, and filter behavior is complete.

Optional chosen-folder clip downloads must stay entirely client-side through browser APIs. Do not send local filesystem path data to the backend or persist it server-side.

Timelapse sessions should store source frames and rendered MP4 output locally under the recordings tree, for example `recordings/timelapses/<printer_id>/<session_id>/`. Do not store timelapse files on printers, do not add NAS sync logic, and do not add database-backed timelapse tracking.

---

## Docker

Docker is the primary deployment method.

Requirements:

- single container
- ffmpeg installed inside container
- host bind mounts for:
  - config
  - recordings
  - logs

Do not introduce multi-container orchestration unless explicitly required.

Avoid Kubernetes complexity.

Installer/update helpers may be added in a future phase, but they must preserve local config, recordings, clip metadata, and review metadata.
Bundled go2rtc support must be optional; external go2rtc instances must remain fully supported.

---

# Code Organization

Code should remain modular and predictable.

Recommended modules:

config
models
state
recorder
api
util

Responsibilities should remain separated.

Avoid mixing UI, recording logic, and configuration logic.

If legacy GoPro support is touched, keep GoPro HTTP control code out of ffmpeg recorder modules.
If a live printer dashboard is added, keep printer-grouping and printer-status code separate from clip-browser and recorder modules.
If timelapse sessions are implemented, keep timelapse session state, frame capture, Moonraker auto-stop, and render lifecycle separate from normal recording state.

---

# ffmpeg Usage

Recording must be implemented using **ffmpeg subprocess calls**.

Rules:

- build command strings in a dedicated module
- for `rtsp://` inputs, prefer `-rtsp_transport tcp` unless there is a specific reason not to
- default printer-camera recording should target the primary video stream and avoid muxing unrelated streams into MP4
- capture stderr for debugging
- handle process lifecycle cleanly
- terminate processes gracefully when stopping recording

Do not introduce alternative recording frameworks.

Timelapse rendering may use ffmpeg, but active timelapse sessions should be tracked separately from normal camera recording processes so clip recording and timelapse lifecycle do not block each other unnecessarily.

For legacy GoPro cameras, do not force recording through ffmpeg. Use device API control and local clip download instead.

# Configuration

Configuration should remain **file-based JSON**.

Supported configs:

- app config
- camera config

Do not introduce:

- YAML
- environment-only configs
- database configs

Configuration files should be easy for a user to edit manually.

Printer-first camera config with top-level `printers` is the preferred direction.
Legacy top-level `cameras` config must remain loadable unless a migration phase explicitly removes it.
Recording and clip storage remain camera-id based even when the UI and config are printer-centered.
The `/cameras` management UI should be printer-first: users manage printers, then nested camera views under each printer.
In the UI, label the internal `record_url` field as `RTSP URL` and keep long preview/RTSP URLs wrapped inside cards.
When `/printers` shows both printer state and recording state, recording labels must be explicit, for example `Recording: Idle`.
Dense `/printers` optional details may use native collapsible sections, but recording controls should remain directly visible.
Deleting printers or cameras from config must not delete local recordings or clips.

The `/live` camera wall polling must not reload or replace preview iframes during normal status refresh.
Update status text in place, use CSS `order` for visual sorting, and only touch iframe `src` when the selected view or preview URL actually changes.
Tab-resume recovery and the manual Refresh Streams action are the only intentional `/live` iframe refresh paths outside user-selected view changes.
Those recovery paths must refresh visible mounted iframe previews only and must not rebuild cards, reappend DOM nodes, reset localStorage preferences, or reload the full page.

# Error Handling

Always assume:

- cameras may disconnect
- streams may fail
- ffmpeg may crash

Errors must be:

- logged
- visible in runtime state

Network-device backends must preserve useful request/response diagnostics without turning every failure into a generic error.

The application must not crash if one camera fails.

---

# UI Design Rules

The UI is a **tool interface**, not a product marketing site.

Requirements:

- simple layout
- camera cards
- clear status indicators
- minimal controls
- mobile-friendly layout

Avoid visual complexity.

# Git Workflow

This repository is already connected to GitHub.

Cursor is allowed to:

- create files
- modify files
- stage files
- commit
- push

After completing a meaningful feature or phase:

- create a commit
- push the commit

Use clear commit messages.

Examples:

Phase 0: project scaffold and Docker setup  
Phase 1: camera dashboard and status API  
Phase 2: ffmpeg recording engine  
Phase 3: recording controls UI  

Avoid giant commits.

Prefer smaller logical commits.

---

# Implementation Discipline

Follow the roadmap phases.

Do not implement future phases unless requested.

If a prompt requests Phase 2, do not implement Phase 4 features.

Stay within scope.

---

# When Making Architectural Decisions

Always prefer:

1. simpler design
2. fewer dependencies
3. easier deployment
4. clearer code

Avoid adding infrastructure that increases operational complexity.

---

# If a Feature is Unclear

Choose the simplest practical implementation and document the assumption.

Never block progress waiting for clarification if a reasonable choice exists.
